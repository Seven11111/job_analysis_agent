## 2. 背景与产品目标

当前产品已经覆盖岗位发现、用户主动保存、岗位分析、个人画像与简历维护、投递状态管理和求职 Agent 对话。下一阶段不重做现有岗位管理，而是把这些能力串成持续使用的求职工作流：

```text
发现岗位 → 评估匹配度 → 用户决定是否保存 → 跟踪投递
                                      ↓
                          管理待办、面试与后续行动
                                      ↓
                         Agent 协助查询、计划和操作
```

产品目标：

1. 用户打开工作台即可看到真实的求职进展、待处理事项和近期面试。
2. 用户能从未保存的搜索结果中快速发现更匹配的岗位，并理解推荐理由。
3. 用户可订阅搜索条件，定期查看新岗位；搜索结果仍由用户决定是否进入正式岗位管理。
4. 现有 Agent 能在用户授权与确认下协助维护待办、面试和岗位跟踪。
5. 通过可复现的评测检查 Agent 是否完成任务、正确使用工具并遵守确认边界。

## 3. 延续的产品边界

- 面向本地单用户，不增加账号体系或多租户。
- 继续聚焦中国技术类校园实习岗位。
- 不自动投递，不绕过招聘网站登录、验证码、风控或访问限制。
- 投递状态由用户维护。系统不得根据搜索、推荐或 Agent 推测某岗位已投递、进入面试或获得 Offer。
- 搜索和推荐结果默认是临时结果；用户明确保存后才进入正式岗位管理。
- 画像和历史偏好用于辅助筛选与排序；本次明确输入优先于长期偏好，临时搜索不得静默改写长期画像。
- 对创建、修改、删除等有副作用的 Agent 操作，先展示操作提案并等待用户确认；未确认时不执行。
- Provider 失败、数据未知和来源差异必须如实呈现；不以 Fixture 或推测补成真实结果。
- 继续遵循现有隐私边界：敏感个人信息不进入模型上下文；日志和评测记录尽量只保留完成任务所需的信息。

## 4. 产品结构与版本路线

产品逐步形成四个互相连接的模块：

| 模块 | 主要职责 |
|---|---|
| 岗位发现 | 多来源搜索、筛选、订阅查新和岗位变化提示 |
| 智能推荐 | 使用明确搜索条件与候选人画像排序，并解释匹配依据 |
| 求职工作台 | 岗位流程、待办、面试日历和真实进度概览 |
| 求职 Agent | 通过对话查询和提出工作台操作，确认后执行写操作 |

| 版本/阶段 | 主题 | 主要范围 | 优先级 |
|---|---|---|---|
| v0.2.0 / Phase 9 | 求职工作台 2.0 | 自定义状态看板、待办、面试日历、基础统计 | P0 |
| v0.2.0 / Phase 10 | 智能岗位推荐 | 搜索结果个性化排序、匹配解释、用户反馈 | P1 |
| v0.2.0 / Phase 11 | 岗位订阅 | 保存条件、手动/定期查新、去重和站内提示 | P1 |
| v0.2.0 / Phase 12 | Agent 工作台协作与评测 | 对话管理待办/面试/订阅、操作确认、任务轨迹和回归评测 | P1 |
| 后续候选 | 信息更新检测、简历定向优化 | 在前述工作流稳定后再评估范围 | P2 |
| 暂缓 | AI 模拟面试、自动化浏览器操作 | 不纳入 v0.2.0 承诺 | P3 / 非目标 |

Phase 9–12 共同构成 v0.2.0 的版本范围，按实施计划分阶段建设和验收，不拆成四个独立版本发布。按用户决定，Phase 9 先行开发；Phase 7 前后端联调、Phase 8 稳定性/安全检查及 Phase 9–12 用户浏览器验收现已完成。P0/P1 表示该版本内的实现优先级。

## 5. v0.2.0：求职工作台 2.0

### 5.1 目标与页面结构

工作台是求职流程的看板和功能入口，不是宣传页。页面仅展示数据库中真实存在、且由用户或系统明确记录的数据；无数据时展示清楚的空状态和下一步入口，不使用演示岗位、虚构进度、虚构面试或虚构统计。

建议页面由以下区域构成：

1. **进度概览**：当前跟踪岗位数、待完成待办数、近期面试数等有明确定义的计数。
2. **投递流程看板**：按用户自定义状态展示岗位卡片，支持搜索、过滤和进入岗位详情。
3. **近期待办**：展示待处理、临近截止和逾期任务，并提供创建、完成和调整入口。
4. **近期面试**：按时间展示面试安排，并提供新增、编辑和查看入口。
5. **求职分析**：展示岗位状态分布、状态变化趋势和待办完成情况等可追溯统计。
6. **快捷入口**：进入岗位搜索、岗位管理、个人画像/简历和求职 Agent。

### 5.2 自定义状态看板

- 看板列来自用户当前启用的状态定义，不在界面或统计逻辑中写死“已投递、笔试、一面、Offer”等固定列。
- 看板顺序遵循用户配置的状态顺序；用户停用或调整状态后，看板同步变化。
- 用户在看板中执行拖拽或状态选择，属于明确的用户状态修改；必须复用现有状态变更流程，记录生效时间、备注和状态事件。
- 看板可按岗位名称/公司、城市、岗位方向和时间范围筛选，并可进入岗位详情。
- 系统不因为用户创建面试记录而擅自变更岗位状态；用户可以在同一流程中显式修改状态。

### 5.3 待办事项

- 支持用户创建、查看、编辑、完成、延期和删除待办。
- 待办可关联一个已保存岗位，也可作为个人通用求职任务独立存在。
- 待办至少能表达标题、关联岗位（可空）、截止时间（可空）、优先级、完成状态和备注。
- 支持从岗位分析的后续建议生成待办提案；用户确认后才创建，不能将模型建议直接写入。
- 删除或完成操作应有清晰反馈；逾期判定依据用户设定的截止时间和本地时区。

### 5.4 面试安排

- 支持新增、查看、编辑和删除面试安排，可关联已保存岗位。
- 面试信息至少包括公司/岗位、轮次或标题、开始时间、结束时间（可空）、时区、形式、地点或会议链接（可空）及用户备注。
- 时间以北京时间作为本地默认展示；用户可修改时间。Agent 遇到日期或时间不完整时必须询问，不得补猜。
- 提供近期列表以及月/周日历视图；可从面试安排创建关联准备待办。
- 面试记录是用户输入的数据，不意味着系统已经核实企业通知，也不自动改变岗位状态。

### 5.5 统计口径

- 概览数字必须能够追溯到岗位跟踪、状态事件、待办和面试记录。
- 可展示当前岗位状态分布、按周的状态事件数量、岗位方向分布、待办完成/逾期数量。
- 仅凭当前状态数量不得计算“投递转化率”或历史漏斗。若后续提供漏斗，必须有明确的状态阶段映射和事件口径；无法映射的自定义状态应列为未分类，不得静默归入某阶段。
- 历史趋势基于记录的事件时间；修改状态生效时间时需按既定历史口径处理，不能把当前状态倒推成历史事件。
- 空数据时显示“暂无记录”及相关入口，不显示 0% 成功率等容易误导的指标。

### 5.6 v0.2.0 验收标准

- 空数据库和已有数据两种情况下均能正确展示；没有记录时无虚构内容。
- 看板列和顺序来自用户状态配置，状态修改后当前状态和历史时间线一致。
- 待办与面试的新增、编辑、完成/延期和删除可以持久化，刷新后仍正确。
- 工作台统计与来源记录可核对，不能把搜索结果当作已保存岗位或已投递岗位。
- 主要模块均有明确入口；前端不直接读取数据库。

## 6. 智能岗位推荐（Phase 10）

### 6.1 功能范围

- 在用户提交搜索后，对本次临时搜索结果提供个性化排序；不要求用户先收藏岗位。
- 用户本次明确指定的关键词、公司、城市、来源和日期条件优先于长期画像。
- 规则层处理明确的硬条件，例如地点、学历、实习可用时间及用户明确选择的来源；未知字段标记为未知，不当作满足条件。
- 对规则筛选后的候选结果进行相关性排序；可以对有限候选岗位调用模型做语义匹配，避免对全部结果无差别深度分析。
- 首版在本地使用已确认的求职偏好和当前在线简历进行可解释规则排序，不调用模型；附件简历只有在用户确认解析并生成在线简历后才参与。没有可用画像资料时按最新发布日期排序，并提示完善资料。
- 每条推荐展示匹配依据、与画像对应的技能/经历、已知差距和未知信息；分数是排序辅助，不是录用概率或客观胜任保证。
- 用户可标记感兴趣/不感兴趣，并撤销或调整反馈；一次反馈不自动修改长期画像。若要将反馈沉淀为长期偏好，需让用户确认。
- 首版反馈只保存在当前服务进程的临时搜索结果中；智能排序时感兴趣结果前置、不感兴趣结果后置。服务重启后清除，不写入长期画像或岗位数据库。
- 推荐结果保持临时状态。只有用户点击保存并确认后，才进入岗位主数据和个人跟踪流程。

### 6.2 验收标准

- 排序严格基于本次搜索允许的来源与条件，不越过来源配置、不扩大城市或时间范围。
- 能区分符合、未满足和来源未提供的条件，并在界面说明原因。
- 每条推荐理由能映射到岗位内容或用户画像，不输出无证据的技能结论。
- 推荐、点击和反馈不会自动收藏岗位、变更投递状态或修改画像。
- 在标注用例上评估硬条件误入、推荐排序和理由可追溯性；报告样本数和判定规则。

## 7. 岗位订阅与查新（Phase 11）

### 7.1 功能范围

- 用户可保存一组岗位搜索条件作为订阅，包含关键词、城市、日期范围、薪资条件、来源和其他当前支持的筛选项。
- 订阅频率支持仅手动、每天、工作日、每周、每隔 2–30 天及每月指定日期；所有自动计划都可设置北京时间 `HH:mm`（24 小时制、精确到分钟），并在界面预览计划。调度器按分钟边界检查；每月目标日期在短月中按当月最后一天执行。
- 用户可在岗位查新列表直接编辑名称、频率和运行时间；搜索关键词、城市、来源等筛选条件从同一编辑弹窗进入岗位搜索调整，避免把计划设置藏在搜索表单中。
- 订阅只能使用用户已配置且明确启用的合规来源；来源授权、登录状态或配置失效时，明确显示来源失败，不静默切换到未选择来源。
- 每次运行展示执行时间、各来源状态、新匹配数量、失败原因和结果预览。新岗位可在订阅结果中查看，用户确认保存后才进入正式岗位管理。
- 为查重和展示订阅结果，可以保存必要的订阅运行记录及短期预览数据；岗位预览保留 30 天，去重哈希和运行摘要在用户删除订阅前保留。不得因此自动创建岗位收藏、投递记录或岗位分析。
- 通过稳定来源 ID 或规范化岗位链接去重。跨来源仅能在证据充分时提示疑似重复，不得无依据合并或丢失来源。
- “本次未搜索到”不代表岗位关闭、过期或停止招聘；仅来源明确提供状态或用户主动修改时才更新生命周期。
- 有来源明确截止日期时可提示临近截止；未知截止日期不推测。
- 第一版提醒限于应用内订阅更新和待处理提示；不接入 QQ、邮件、短信或其他外部消息渠道，这些属于后续版本。

### 7.2 本地运行约束

- 应用内定时执行仅在后端运行期间可用。界面必须说明该限制，提供手动查新入口和上次运行状态。
- 不承诺设备关机、后端退出或系统休眠期间仍定时运行；恢复运行后的补查策略在实现阶段明确并可由用户识别。
- v0.2.0 不引入 Redis、Celery、Kafka 等重型队列。若后续实际任务量证明单进程调度不足，再单独评估。

### 7.3 验收标准

- 用户可以创建、修改、暂停、恢复、手动执行和删除订阅。
- 相同岗位在同一订阅中不会被重复提示；不同来源的记录仍能查看来源和原始链接。
- 订阅失败与“没有新岗位”清楚区分；部分来源失败不会被伪装为完整成功。
- 订阅运行结果不自动成为正式岗位、收藏或分析记录。
- 后端停止时不声称任务仍会执行；重新启动后状态和上次运行时间可解释。

## 8. Agent 工作台协作与评测（Phase 12）

### 8.1 Agent 能力

- Agent 可根据当前任务查询工作台摘要、岗位状态、待办、面试安排、推荐结果和订阅运行状态。
- Agent 可将自然语言请求转换为一个或多个可审阅的操作提案，例如创建准备待办、记录面试安排、修改待办截止时间或暂停订阅。
- 只读查询可以直接执行；任何创建、修改或删除都必须显示目标对象、拟变更内容和必要时间信息，并等待用户确认。
- 用户拒绝或关闭提案时不执行；用户未处理时保持待处理，不能因模型回答结束、SSE 断开或切换界面而悄悄丢弃待确认操作。
- 多步骤请求在缺少必要信息时先澄清；确认后逐项执行，并报告部分成功、失败和未执行项。
- Agent 复用现有会话与上下文机制，不创建单独的工作台聊天机器人，不把全部简历、岗位和长期记忆无差别塞入模型上下文。
- 不引入多 Agent 编排作为展示性功能；优先保证现有 Agent 的工具路由、参数校验、幂等性和恢复行为。

### 8.2 任务轨迹与评测

- 可观测信息用于排查 Agent 是否选择了正确工具、参数是否正确、操作是否等待确认及最终状态是否达成。
- 记录任务阶段、工具名称、必要的脱敏参数摘要、工具结果类别、耗时和错误类型；不把隐藏思维链作为评测数据或用户功能。
- 建立覆盖岗位搜索、岗位/画像查询、待办与面试读写、订阅操作、多轮上下文、澄清、来源失败和确认边界的回归用例。
- 至少分别报告：任务完成率、工具选择/顺序准确率、参数准确率、写操作确认安全性、失败恢复结果和响应耗时；写明评测集规模、运行次数、模型/Provider 和环境。
- 小样本结果只能称为项目自测或功能验证，不表述为线上成功率、生产 SLA 或普遍模型能力。

### 8.3 验收标准

- Agent 可以在一个会话中查询相关工作台数据并正确引用记录，不把临时搜索结果误报为已保存岗位。
- 写操作在用户确认前数据库状态不变；拒绝、重复确认、超时和 SSE 断开均不会造成未授权或重复变更。
- 多对象操作可报告每项结果，失败不会掩盖已完成和未完成部分。
- 自动化回归测试检查工具、参数、最终数据状态和确认边界；评测报告可复跑并包含样本范围与限制。

## 9. 统一非目标

v0.2.0 不包括：

- 自动投递、代替用户与招聘方沟通或自动填写第三方网站表单。
- 绕过登录、验证码、风控、付费墙或招聘平台访问限制。
- 多用户、团队共享、云端账号体系。
- 保证后端关闭时仍可靠运行的全天候订阅服务。
- 邮件、短信或第三方即时通讯推送。
- 复杂多 Agent 系统、复杂向量记忆、通用网页自动化浏览器操作。
- AI 模拟面试的完整产品化能力。
- 未经用户确认修改画像、岗位状态、简历或其他长期数据。

岗位信息变化检测、简历定向优化和模拟面试可在 v0.2.0 验收后依据使用情况另行立项，不自动纳入本版本范围。

## 10. 数据、接口与架构影响

本 PRD 不锁定具体表名和 API 路径。实现各版本时应按实际需要更新相应设计文档：

- 工作台可能新增待办和面试记录数据，并复用既有岗位跟踪状态、状态事件和岗位分析。
- 推荐能力消费临时搜索结果、当前画像和可选简历上下文；不得为排名而把全部搜索结果写入正式岗位表。
- 订阅需要保存搜索条件、运行状态和去重所需的最小观察记录；订阅预览与正式岗位数据边界必须保持清楚。
- Agent 工具与操作提案应复用现有 SSE、会话和确认机制；新写操作需要明确幂等和恢复行为。
- 数据库变化必须通过项目现有迁移流程完成；具体接口字段、错误语义和事件格式写入 API 契约，而非只停留在本 PRD。

## 11. 风险与设计护栏

| 风险 | 护栏 |
|---|---|
| 自定义状态被错误套入固定漏斗 | 看板读取用户状态；漏斗要求显式映射，未映射状态不推断 |
| 搜索/推荐被误当成已收藏或已投递 | 临时结果与正式岗位管理分离，只有用户确认保存才入库 |
| 模型输出虚构岗位匹配点 | 每条理由需引用岗位或画像证据；缺失数据标为未知 |
| 订阅误判岗位关闭 | 无结果不代表关闭，只有明确来源证据或用户操作才改变状态 |
| 本地应用关闭导致漏跑订阅 | 明确提示运行前提，提供手动执行、运行历史和失败状态 |
| Agent 未确认就执行或重复写入 | 待确认提案持久化；确认接口校验状态并保证重复处理安全 |
| 评测数字被过度宣传 | 保存测试定义、样本数、运行轮数与环境，禁止把小样本写成生产保证 |

## 12. 文档版本维护

- `PRD.md` 保留 MVP 已确认需求基线；本文件是 v0.2.0 起的后续产品更新基准。
- `PRD-v0.2.0.md` 的修改只代表 v0.2.0 需求在评审/实施中的澄清，不代表相应功能已经发布。
- 若 v0.2.0 完成后产品范围出现新的实质性版本变化，新增 `PRD-v0.3.0.md` 等版本文件，并在文档中说明继承和替代关系；不要为每次文字修正复制一个新文件。
- `docs/CHANGELOG.md` 记录实际代码与文档交付；规划中但未实现的内容不放入已发布版本说明。
- 每个阶段完成后同步更新实施计划、架构/数据/API 文档和变更记录，并保留测试与验收结果。
